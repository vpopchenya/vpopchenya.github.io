# CLAUDE.md

Контекст проекта для Claude и для меня самого: что это за сайт, как он устроен, какие решения мы приняли и каких правил держимся. Файл написан по итогам первой сессии разработки (24 октября 2026) и дополнен после ревью в тот же день.

## Что это

Личный сайт-визитка Вадима Попченя (GitHub: `vpopchenya`). Он нужен для двух целей:

- показать себя как автотестировщика (Python, pytest, Playwright, позже Locust);
- продавать сайты: лендинги, корпоративные и многостраничные.

Главная мысль страницы: **«Делаю сайты и сам проверяю их»**. Каждый сайт проходит автотесты до сдачи, за качество можно не волноваться.

Адрес: `https://vpopchenya.github.io` (русская версия) и `https://vpopchenya.github.io/en/` (английская). Размещён на GitHub Pages, это статический сайт без сборки.

## Правила работы с этим проектом

Это договорённости с владельцем, их нужно соблюдать в каждой сессии.

1. **Сначала вопросы, потом действия.** Перед любым действием, особенно публикацией, коммитом, включением настроек или созданием контента, который увидят люди, задавай уточняющие вопросы. Так результат получается лучше.
2. **Сначала показать, потом публиковать.** Новую версию сначала показывай в виде превью (закрытая страница или файл) и публикуй на GitHub только после явного «да» владельца.
3. **Не выдумывать публичные данные.** Контакты и цены сейчас заглушки. Не подставляй чужие или придуманные значения, не размещай их в структурированных данных (JSON-LD).
4. **Заглушка не должна быть рабочей ссылкой.** Ссылка вида `t.me/username` ведёт на чужой аккаунт. Пока контакта или работы нет, показывай неактивную строку «скоро появится», а не ссылку.
5. **Не создавать аккаунты и не вводить ключи** вместо владельца. Ключ формы он получает сам.
6. **Общение по-русски**, коротко и по делу. Проверяй все ключевые ширины: 1920, 1280, 768 и 390 px, плюс обе стороны каждой точки перестройки вёрстки (901/900 и 761/760 px). Скриншоты смотри на 1920, 1280, 768 и 390 px.
7. **Публикация через git, а не перепечатыванием файлов.** Если файлы приходится передавать текстом через API, после публикации обязательно сверяй репозиторий с исходниками (`git clone` и `cmp`). Так однажды уже нашлась опечатка, появившаяся при передаче.
8. Владелец учится автотестированию: тесты на Python, pytest, Playwright (UI), requests и httpx (API), позже Locust (нагрузка). Репозиторий для обучения: `vpopchenya/python-autotests-learning`. Менеджер пакетов: начинаем с pip + venv + `requirements.txt`, позже можно перейти на PDM.
9. **У каждого нового элемента, который может понадобиться автотесту, сразу ставь `data-testid`** (правила ниже, в разделе «Атрибуты для автотестов»). Сайт служит образцом «проверяю автотестами», поэтому разметка для тестов делается сразу, а не потом.
10. **Код поддерживаемый и понятный.** Пиши так, чтобы через полгода его можно было расширять и дописывать, не разбираясь заново. Конкретные правила в разделе «Как писать код».

## Как писать код

Цель: код можно расширять и дописывать без того, чтобы разбираться в нём заново. Это касается и сайта, и тестов.

**Общее**
- **Одно место для одной вещи.** Цвет в переменной `:root`, общий стиль в общем правиле (как «стекло» у `.card`, `.plan`, `.order`), повторяющиеся проверки в одной функции. Если копируешь блок второй раз, вынеси его.
- **Понятные имена.** Классы по смыслу (`.plan`, `.form-status`), а не по виду (`.yellow-box`). Переменные и функции в JS и Python называются тем, что они делают.
- **Комментарий объясняет «почему»**, а не пересказывает код. Хороший пример: «печать начинает анимацию увеличенной вдвое, поэтому `overflow-x: clip`». Плохой: «задаём overflow». Если решение неочевидно или было найдено после ошибки, напиши это в комментарии рядом и в этом файле.
- **Без мёртвого кода.** Неиспользуемые стили, функции и закомментированные куски удаляй, история есть в git.
- **Без хаков, если есть нормальное решение.** `!important` только для служебных случаев (`[hidden]`, `prefers-reduced-motion`), иначе поднимай специфичность селектора. Не подбирай отступы «на глаз», чтобы что-то выровнять: используй сетку (`subgrid`, `gap`).
- **Небольшие шаги.** Одно изменение, проверка, следующее. Коммит на одну логическую правку, с понятным сообщением.

**HTML**
- Семантические теги (`header`, `main`, `section`, `article`, `form`, `fieldset`), одна `h1`, у полей `label`.
- RU и EN устроены одинаково: те же классы, `id`, `data-testid` и порядок элементов. Отличается только текст. Так любую правку можно повторить во второй версии механически.
- Заглушки помечены комментарием `ЗАГЛУШКА` / `PLACEHOLDER` с подсказкой, на что их заменить.

**CSS**
- Порядок в `style.css`: переменные и база, затем блоки страницы сверху вниз (шапка, главный экран, секции, форма, подвал), затем служебные страницы, **в конце все медиазапросы** (точки 900 и 760 px) и `prefers-reduced-motion`.
- Каждый блок начинается с короткого комментария, что это.
- Новые цвета, шрифты и размеры, которые повторяются, сразу в переменные.

**JavaScript**
- Без библиотек и сборки, пока сайт статичный. Один файл `main.js`, внутри блоки по функциям с комментарием сверху.
- Тексты для человека не пишутся в JS, они берутся из HTML (`data-msg-*`), поэтому один скрипт работает на обоих языках.
- Скрипт не должен ломать страницу, если какого-то элемента нет: проверяй наличие (`if (!form) return`).

**Тесты (pytest + Playwright)**
- Локаторы только по `data-testid`, роли или `label`, а не по классам и тексту.
- Структура на вырост: `tests/` по страницам и функциям (`test_form.py`, `test_layout.py`), общие вещи в `conftest.py` (адрес сайта, браузер, список ширин), ширины и страницы задаются через `@pytest.mark.parametrize`, а не копированием теста.
- Когда тестов станет больше, повторяющиеся действия выносятся в классы страниц (Page Object): `HomePage.order_form.fill(...)`.
- Название теста говорит, что проверяется: `test_form_without_key_shows_note_and_disables_submit`.
- Каждый новый найденный баг получает свой тест, чтобы он не вернулся (как тест на сдвиг страницы вбок во время анимации печати).

## Атрибуты для автотестов (data-testid)

Элементы, которые проверяют тесты, помечены атрибутом `data-testid`. В Playwright по нему ищут так: `page.get_by_test_id("form-submit")`. Тесты на `data-testid` не ломаются, когда меняется текст, перевод или оформление.

**Правила:**
- имена английские, в kebab-case, **одинаковые в RU и EN** (один тест проверяет обе версии);
- имя описывает роль элемента, а не текст и не цвет: `form-submit`, а не `send-button-yellow`;
- уникальны в пределах страницы. Повторяются только однотипные элементы внутри разных карточек (`plan-price`, `plan-order`). Их ищут внутри карточки: `page.get_by_test_id("plan-landing").get_by_test_id("plan-order")`;
- элементы, которые создаёт JS, получают `data-testid` в коде (`form-note` в `main.js`);
- когда заглушку заменяете настоящим элементом (карточку `<div>` на ссылку `<a>`, строку «скоро появится» на ссылку), **`data-testid` переносится на новый элемент без изменений**;
- `data-testid` не используется в CSS и JS-логике, только в тестах. Для стилей есть классы;
- после правки разметки сравните наборы в обеих версиях: `diff <(grep -o 'data-testid="[^"]*"' index.html) <(grep -o 'data-testid="[^"]*"' en/index.html)`.

**Что размечено:**

| Где | `data-testid` |
|---|---|
| Шапка (все страницы, кроме 404) | `logo`, `lang-switch`, `lang-ru`, `lang-en` |
| Главный экран | `skip-link`, `stamp`, `hero-title`, `hero-order` |
| Секции | `section-what`, `section-prices`, `section-works`, `section-order`, `section-contacts` |
| «Чем занимаюсь» | `panel-tests`, `panel-sites` |
| Цены | `plan-landing`, `plan-corporate`, `plan-multipage`, внутри каждой `plan-price`, `plan-order` |
| «Мои сайты» | `work-card-1`, `work-card-2`, `works-order` |
| Форма | `order-form`, `form-note` (только пока нет ключа), `form-name`, `form-contact`, `type-landing`, `type-corporate`, `type-multipage`, `type-other`, `type-unsure` (на `<label>` таблетки), `form-other-box`, `form-other`, `form-unsure-hint`, `form-message`, `form-botcheck`, `form-consent`, `form-privacy`, `form-submit`, `form-status` |
| Контакты | `contact-github`, `contact-telegram`, `contact-email` |
| Подвал | `footer`, `footer-privacy` |
| Политика | `privacy-page`, `privacy-email` (обе заглушки адреса), `back-home` |
| 404 | `notfound`, `notfound-home`, `notfound-en` |

## Дизайн

- **Идея:** тёмная страница, на которой синий свет только как акцент, и цветные «стеклянные» карточки. Вся страница о качестве и проверке, поэтому повторяется мотив галочки «тест пройден».
- **Цвета** (переменные в `:root`): фон `--bg #0e0a2b`, акцентный синий `--blue #3a2eff` (свечение сверху справа и снизу слева, переключатель языка), жёлтый `--yellow #ffd23f` (кнопки), розовый `--pink #ff8ac2`, мятный `--mint #7dffd0`, тёмные надписи `--ink #14103a`. Для кнопок: `--yellow-hover #ffdc66` (наведение) и `--yellow-step #b98f00` (ступенька под кнопкой). Раньше фон был целиком синий, владелец сказал, что синего слишком много, поэтому фон стал тёмным. Новые цвета добавляй переменными, а не числами в коде.
- **Шрифты:** системные (`system-ui`, `Segoe UI`, `Roboto` и т. д.), без загрузки файлов, одна переменная `--font`. Заголовки с весом 700, спокойные. Раньше были Unbounded и Manrope, но их файлы не удалось скачать в среде разработки, а без шрифтов страница быстрее. Если захотите вернуть фирменный шрифт, кладите файлы woff2 в `fonts/`, добавляйте `@font-face` и `font-src 'self'` в политику безопасности.
- **Логотип:** монограмма VP на жёлтом скруглённом квадрате. Буква V нарисована как галочка. Встроен в шапку как inline SVG, тот же знак в `favicon.svg`. Полное имя остаётся в `aria-label` и в `<title>`.
- **Фон страницы:** фиксированный слой `.bg`: два полупрозрачных окна браузера с макетами сайтов (визитка и лендинг) и фрагменты кода тестов Playwright и отчёта pytest. Всё нарисовано в коде (SVG и текст), без картинок. Яркость низкая, чтобы не мешать чтению.
- **Структура страницы:** шапка (логотип и переключатель языка), главный экран, «Чем занимаюсь», «Услуги и цены», «Мои сайты», «Заказать сайт» (форма), «Контакты», подвал.

## Анимации

Движение сдержанное: одно «событие» на загрузку, остальное отвечает на действия человека.

- **Загрузка страницы:** строки главного экрана выезжают снизу по очереди (`.intro`, задержки 0,05 / 0,25 / 0,4 с), затем розовая печать «тесты пройдены» «штампуется» (`@keyframes stamp`). Работает на чистом CSS, без JavaScript. Печать начинает анимацию увеличенной вдвое и в начале выходит за правый край окна. Поэтому у `<html>` стоит `overflow-x: clip`, иначе первые ~1,5 с страницу можно было сдвинуть вбок (найдено проверкой на 768–1280 px). **Не убирайте `overflow-x: clip`, пока анимация печати такая.**
- **Появление секций при прокрутке:** `IntersectionObserver` добавляет класс `.in` один раз. Секции прячутся, только если в `<head>` выполнился маленький скрипт (класс `js` на `<html>`).
- **Страховка появления секций:** если `main.js` не загрузился или упал, через 2,5 с CSS-анимация `reveal-safety` всё равно показывает все секции. Когда `main.js` работает, он первым делом ставит на `<html>` класс `reveal-ready`, и страховка отключается. Раньше без `main.js` страница ниже первого экрана оставалась пустой. **`classList.add("reveal-ready")` должно оставаться первой строкой `main.js`.**
- **Фон с параллаксом:** окна и код при прокрутке смещаются медленнее страницы, у каждого своя скорость (`data-speed`). Обновление через `requestAnimationFrame`, события прокрутки пассивные.
- **Плавная прокрутка** по якорям (`scroll-behavior: smooth`).
- **`prefers-reduced-motion`:** если в системе включено «уменьшить движение», все анимации, переходы и параллакс отключаются, контент сразу виден.
- Анимируй только `transform` и `opacity`: так браузеру не нужно пересчитывать раскладку страницы. Свойства, которые только перерисовывают элемент (цвет, `border-radius`, `background-size`), допустимы. Свойства, которые меняют размеры и положение (`padding`, `margin`, `top`, `width`), анимировать нельзя: сдвиг контактов и ссылки «Перейти к содержимому» сделан через `transform`.

## Наведение и интерактив

- **Текст-маркер:** описание на главном экране и тексты в блоках «Автотесты» и «Сайты» при наведении заливаются цветом, как будто выделены маркером (`.sweep`).
- **Кнопки объёмные:** жёлтая «клавиша» с тёмно-жёлтой ступенькой снизу. При наведении приподнимается, при нажатии вдавливается, стрелка справа сдвигается. Один стиль на всех кнопках сайта.
- **Карточки поднимаются при наведении** на 16 px (карточки цен, «Мои сайты») и на 14 px (блоки «Автотесты» и «Сайты»), с цветной тенью и сменой рамки на цвет карточки.
- **Свет следует за курсором** в карточках «Мои сайты» (CSS-переменные `--mx`, `--my`, их задаёт JS).
- **Миниатюры сайтов** в карточках слегка наклоняются при наведении.
- **Ссылки:** адреса в контактах розовые, при наведении становятся мятными, под ними выезжает линия, название слева желтеет и сдвигается. Ссылки на политику в форме тоже розовые.
- **Заглушки контактов** (`.soon-row`) выглядят как строка контакта, но приглушены, без ссылки и без эффектов наведения.
- **Заголовок** на главном экране при наведении сдвигается и желтеет. Логотип наклоняется.
- **Фокус с клавиатуры:** жёлтая рамка у всех интерактивных элементов, есть ссылка «Перейти к содержимому».

## Карточки

- **«Услуги и цены»:** три стеклянные карточки: Лендинг (от 15 000 ₽), Корпоративный сайт (от 40 000 ₽), Многостраничный сайт (от 70 000 ₽). **Цены ориентировочные заглушки**, в коде помечены комментарием. Под карточками написано, что точную цену называют после разговора. Кнопка «Заказать» ведёт к форме и сама выбирает нужный тип. Названия тарифов крупные, у каждой карточки свой цвет акцента (жёлтый, мятный, розовый). На компьютере (от 901 px) карточки делят общие строки через `grid-template-rows: subgrid`: название, описание, цена, список и кнопка стоят на одном уровне при любой длине текста. Раньше выравнивалась только высота названий, и на 1920 (EN) и 901 (RU) px цены оказывались на разной высоте. В браузерах без `subgrid` остаётся запасной вариант с `min-height`. **В карточке цены должно быть ровно 5 дочерних элементов** (`h3`, `.for`, `.price`, `ul`, кнопка), иначе сетка собьётся.
- Стиль «стекла» общий для `.card`, `.plan` и `.order` (один блок в CSS).
- **«Мои сайты»:** две карточки-заглушки «Место для первого проекта» и «Место для второго проекта» с меткой «Скоро». Это `<div>`, а не ссылки: заглушка не должна обещать переход. Раньше там были выдуманные названия (кофейня, мастер на час), их убрали, чтобы клиент не принял их за настоящие работы. Когда появится сайт, замените `<div class="card">` на `<a class="card" href="адрес">`. Эффект матового стекла (`backdrop-filter`) с цветным свечением, цветные пятна света стоят позади, чтобы размытие было видно.

## Форма заявки

- Поля: имя, контакт (Telegram или email), тип сайта, описание, согласие на обработку данных, скрытая ловушка для ботов (`botcheck`).
- **Тип сайта** выбирается «таблетками» (радиокнопки), а не выпадающим списком: системный список выглядел плохо и отличался в браузерах. Варианты: Лендинг, Корпоративный сайт, Многостраничный сайт, **Другое** (по клику открывается обязательная строка «Что именно нужно»), **Пока не знаю** (короткая подсказка, поле описания необязательное).
- Отправка: `fetch` на `https://api.web3forms.com/submit` (сервис Web3Forms, письмо приходит на почту владельца). Ключ вставляется в `data-key=""` у `<form id="order-form">` в обеих версиях. **Пока ключа нет, форма ничего не отправляет:** сразу над полями видно жёлтое сообщение «Форма пока не подключена» (текст из `data-msg-nokey`, элемент создаёт `main.js`), кнопка «Отправить заявку» выключена. Раньше человек узнавал об этом только после заполнения всей формы. С ключом сообщение не появляется, кнопка работает.
- Сообщения формы не отсылают к Telegram, пока Telegram заглушка. Когда появится настоящий контакт, можно снова добавить его в `data-msg-err`, чтобы у клиента был запасной путь.
- Проверки: HTML-валидация, повторная отправка блокируется во время запроса, таймаут 15 секунд, сообщения об успехе и ошибке на двух языках, без cookie (`credentials: "omit"`), без передачи реферера.
- **Перед подключением ключа** проверьте требования закона о персональных данных (раздел «Закон и данные» ниже).

## Закон и данные (152-ФЗ)

Это не юридическая консультация, а список того, что нужно проверить до включения формы:

## SEO

- У каждой страницы свой `<title>`, `description`, `canonical`, `hreflang` (ru, en, x-default), `lang` на `<html>`, одна `<h1>`, нормальная структура заголовков.
- Open Graph и Twitter Card с картинками 1200x630 (`img/og-ru.png`, `img/og-en.png`), `og:locale`, альтернативные локали. **Картинки пока не загружены в репозиторий** (инструмент публикации не передаёт двоичные файлы), их нужно добавить вручную через GitHub или git.
- JSON-LD: `WebSite` и `Person` (имя, профессия, GitHub, область знаний). У `Person` на обеих страницах один `@id` и один `url` (главная). **Телефон, email и цены в структурированные данные не попадают**, пока это заглушки.

- Иконка, `theme-color`, семантические теги, текст на двух языках лежит прямо в HTML.
- **Честно:** первое место по общим запросам («сайт-визитка заказать») не гарантирует никакая настройка. По запросу с именем «Вадим Попченя» это реально. Дальше нужны: регистрация в **Google Search Console** и **Яндекс Вебмастере**, отправка `sitemap.xml`, **свой домен**, ссылки на сайт с GitHub, Telegram и площадок (Kwork, Авито, Профи.ру), реальные работы в блоке «Мои сайты».

## Производительность

- Вся страница вместе с CSS и JS около 12 КБ в сжатом виде (HTML около 5 КБ, CSS около 5 КБ, JS около 1,5 КБ), без шрифтов, без сторонних скриптов, без аналитики и внешних запросов (кроме отправки формы).
- Скрипт подключён с `defer`, маленький inline-скрипт ставит класс `js`.
- Картинки на странице не используются (всё в SVG и CSS), картинки для соцсетей нужны только поисковикам и мессенджерам.
- **Когда появятся настоящие картинки** (скриншоты работ): формат WebP или AVIF, ширина не больше нужной (обычно до 1600 px), атрибуты `width` и `height` (чтобы страница не прыгала при загрузке), `loading="lazy"` для всего, что ниже первого экрана, осмысленный `alt`.
- Если вернёте внешние шрифты, используйте `font-display: swap`, подмножества (cyrillic, latin) и `preload`.
- Цель: в PageSpeed Insights (Lighthouse) не ниже 90 по всем четырём оценкам на телефоне.

## Безопасность

- **Content-Security-Policy** задана тегом `<meta>` на каждой странице: `default-src 'none'`, скрипты и стили только свои, соединения только с `https://api.web3forms.com`, `base-uri 'none'`, `form-action 'none'`. Встроенный скрипт разрешён по хешу `sha256`: **если меняете этот скрипт в `<head>`, пересчитайте хеш**. Новый внешний сервис добавляйте в политику явно.
- `referrer` ограничен (`strict-origin-when-cross-origin`), на внешних ссылках `rel="me noopener"`, на форме нет `action`, данные не уходят никуда, кроме Web3Forms.
- Ограничение GitHub Pages: нельзя задать HTTP-заголовки (`X-Frame-Options`, `frame-ancestors`, HSTS настраивает сам GitHub). Если нужна полная защита, можно позже поставить сайт за Cloudflare или перенести на Netlify и задать заголовки там.
- Сайт отвечает по HTTPS. Галочку «Enforce HTTPS» в Settings, Pages владельцу нужно проверить самому: из среды разработки её не видно.
- **Никаких секретов в репозитории.** Ключ Web3Forms публичный по замыслу сервиса, но токены GitHub, пароли и ключи других сервисов в код и коммиты не попадают никогда. Репозиторий публичный.

## Доступность

- Контраст текста не ниже WCAG AA (4,5:1 для обычного текста). При смене цветов проверяйте контраст, особенно у приглушённых элементов (`opacity`).
- Всё, что работает мышью, работает с клавиатуры. У полей есть `<label>`, у декоративных SVG `aria-hidden="true"`, у кнопок и ссылок понятный текст.

## Как проверять изменения

Быстрый локальный сервер из корня сайта: `python -m http.server 8765`, затем `http://127.0.0.1:8765/`. Что мы проверяли скриптами Playwright:

- нет ошибок в консоли и нарушений CSP, нет запросов с ответами 4xx на всех пяти страницах;
- на ширинах 1920, 1280, 901, 900, 768, 761, 760 и 390 px: страницу нельзя сдвинуть вбок колесом или тачпадом (в том числе сразу после загрузки, пока идёт анимация), нет полосы прокрутки снизу, ни один элемент не вылезает за край, число колонок цен и формы и положение печати соответствуют точкам 900 и 760 px, на компьютере цены стоят на одной линии;
- ссылка «Перейти к содержимому» появляется по Tab, при наведении на контакт строка не меняет размер;
- без ключа форма сразу показывает сообщение и кнопка выключена;
- все секции появляются при прокрутке;
- страницу 404 локально открывайте по адресу `/404.html`: `python -m http.server` на несуществующий адрес отдаёт свою страницу, а не нашу (это умеет только GitHub Pages). На живом сайте проверяйте любой несуществующий адрес;
- в тестах прокрутка мгновенная (`behavior: 'instant'`), потому что на сайте включена плавная прокрутка, а размер ссылки-пропуска меряется после её анимации. Иначе тест видит промежуточное состояние и падает без причины;
- переключение RU ↔ EN в обе стороны;
- форма: без согласия не отправляется, без ключа показывает сообщение, с ключом (подмена сети) отправляет нужные поля, после отправки очищается;
- «Другое» открывает обязательную строку, «Пока не знаю» показывает подсказку, кнопки «Заказать» выбирают нужный тип;
- если заблокировать `main.js`, все секции всё равно появляются через 2,5 с;
- на страницах нет ссылок `t.me` и `mailto:`, пока контакты заглушки.

Дополнительно полезно: [validator.w3.org](https://validator.w3.org/) для HTML, PageSpeed Insights для скорости и доступности, проверка битых ссылок.

Хорошее продолжение для обучения: оформить эти проверки как настоящие тесты pytest + Playwright в репозитории `python-autotests-learning` и запускать их через GitHub Actions при каждом push. Тогда сломанную версию будет видно до того, как её увидит клиент.

## Рекомендации для развития как разработчика сайтов

Это советы на будущее, а не обязательные правила проекта. Отсюда удобно брать следующие задачи.

**Своя «фишка»: проверка качества**
- Соберите **набор автотестов, который подходит к любому сайту**: битые ссылки, ответы 4xx и 5xx, ошибки в консоли, горизонтальная прокрутка на телефоне, отправка формы, скриншоты ключевых экранов. Держите его отдельным репозиторием и запускайте на каждом клиентском сайте.

**Скорость работы**
- Сделайте из этого сайта **шаблон-стартер** (template repository на GitHub): HTML-каркас, SEO-теги, CSP, форма, 404, robots, sitemap, тесты, CLAUDE.md, чеклист. Новый лендинг начинается не с нуля.

## Почему сделано именно так

- **Две страницы вместо JS-переключателя:** для индексации обеих версий в поиске.
- **Системные шрифты:** файлы шрифтов нельзя было скачать, и это самый быстрый вариант.
- **Таблетки вместо выпадающего списка:** системная подсветка пункта плохо читалась на тёмном фоне и выглядела по-разному в браузерах.
- **Тёмный фон:** владельцу казалось, что синего слишком много.
- **Форма через внешний сервис:** у статичного сайта нет сервера, а подключение сервиса остаётся за владельцем (регистрация и ключ).
- **Логотип VP:** владелец захотел свой знак вместо имени и фамилии в шапке.
- **Неактивные заглушки вместо ссылок:** `t.me/username` вёл бы на чужой аккаунт, а выдуманные работы вводили бы клиента в заблуждение.
- **Страховка анимации появления:** контент важнее эффекта, страница не должна оставаться пустой из-за одного файла.
